# Decisions

## D-001 — P0 실기기 게이트를 먼저 통과한다

- 상태: 승인됨
- 근거: `docs/SPEC_v0.2.md` §17–18, `docs/DEV_PLAYBOOK.md` P0
- 결정: 경제와 제품 UI를 구현하기 전에 시스템 프레임워크 조합을 별도 프로브로 검증한다.

## D-002 — XcodeGen으로 프로젝트 정의를 보존한다

- 상태: 승인됨
- 결정: 사람이 리뷰 가능한 `project.yml`을 원본으로 두고 `.xcodeproj`를 생성한다.
- 이유: 신규 멀티 타깃 프로젝트의 build setting, entitlement, target membership을 재현 가능하게 관리하기 위해서다.

## D-003 — P0 로그와 SwiftData 일관성 검증을 분리한다

- 상태: 승인됨
- 결정: 사람이 읽는 프로브 로그는 App Group JSONL에 기록하고, 위젯→앱 정합성 항목은 별도의 최소 SwiftData 모델을 App Group 컨테이너에 직접 써서 검증한다.
- 이유: 오류 원문 관찰성과 Spec §18 #10의 SwiftData 동시 쓰기 위험 검증은 서로 다른 목적이다. 명령 큐는 실기기 실패가 확인될 때만 후속 대응으로 채택한다.

## D-004 — 24pt P0 아이콘은 코드 기반 픽셀 실루엣으로 만든다

- 상태: D-016으로 대체됨
- 결정: AI 생성 이미지를 쓰지 않고 24×24 셀 기반 `Canvas` 실루엣을 사용한다.
- 이유: 픽셀 아트 문서는 작은 아이콘을 수작업 대상으로 분류하고, P0는 식별성 검증이 목적이다.

## D-005 — 공유 JSONL은 프로세스 간 잠금과 상한을 가진다

- 상태: 승인됨
- 결정: app/extension 공용 로그는 POSIX `flock` 아래 append/read/compaction을 수행하고 256KB 초과 시 최근 500줄만 보존한다.
- 이유: 세 프로세스의 동시 append가 JSONL을 손상시키거나 App Group 저장 공간을 무제한 소비하지 않게 한다.

## D-006 — shield 수명주기는 프로세스 잠금과 세션 ID로 보호한다

- 상태: 승인됨
- 결정: App/DeviceActivityMonitor가 같은 App Group 파일 잠금을 사용한다. 각 monitor 이름과 journal에 세션 UUID를 넣고, 일치하는 callback만 settings와 journal을 해제한다. monitor/journal 준비 후 shield를 적용하고 중간 실패·시작 시 orphan 상태를 fail-safe 해제한다.
- 이유: 권한·스케줄 오류나 앱 강제 종료뿐 아니라 이전 monitor callback과 새 세션의 교차 실행이 사용자를 잘못 차단하거나 새 세션의 복구 정보를 지우는 것을 막는다.

## D-007 — 사용자 로그에는 제한된 오류 요약만 저장한다

- 상태: 승인됨
- 결정: 화면과 공유 JSONL에는 오류 domain/code/description을 600자로 제한하고 홈 경로를 치환한다. 전체 오류 반영은 private OSLog에만 남긴다.
- 이유: 진단 가능성을 유지하면서 공유 컨테이너와 화면에 민감한 내부 정보를 노출하지 않는다.

## D-008 — entitlement 소스와 실제 서명 결과를 분리해 판정한다

- 상태: 승인됨
- 결정: `project.yml`에 앱 그룹과 FamilyControls entitlement를 명시하되, 실제 통합 통과는 승인 프로비저닝으로 서명된 산출물의 entitlement와 실기기 동작으로만 판정한다.
- 이유: 코드 서명 비활성화 빌드나 빈 ad-hoc 시뮬레이터 entitlement는 시스템 기능의 성공 증거가 아니다.

## D-009 — Live Activity 교체는 App Group 프로세스 잠금 아래 수행한다

- 상태: 승인됨
- 결정: 앱과 LiveActivityIntent가 같은 잠금 파일을 획득한 뒤 기존 Activity를 최대 3회 재확인·종료하고 새 Activity를 요청한다.
- 이유: 두 프로세스가 동시에 end→request를 수행해 커스텀 Live Activity가 중복 생성되는 경쟁을 차단한다.

## D-010 — P0 UI는 기술/산업형 SHAFT 대시보드로 표현한다

- 상태: D-012로 대체됨
- 결정: `DEEPMINE / SYSTEM SHAFT 00–04`를 화면의 구조 언어로 사용하고, 픽셀아트 문서의 고정 팔레트와 24셀 광부 실루엣을 앱·Live Activity·위젯에 공통 적용한다. 핵심 한국어 동작은 Dynamic Type을 모두 따르고, 장식용 영문 식별자는 XXXL까지만 확대한다.
- 이유: P0의 기술 검증 목적을 숨기지 않으면서 동일 카드와 pill 버튼의 개발자 도구 인상을 제거하고, 향후 제품 표면과 이어지는 DeepMine 정체성을 만든다.
- 상호작용: 주 동작, 보조 동작, 안전 해제, 주의 동작을 색과 명도로 분리하고 press-down은 0.98 scale의 짧은 interruptible spring을 사용한다. Reduce Motion에서는 위치/scale animation을 제거한다.

## D-011 — 화면 증거는 카드 단위 UI 테스트로 재현한다

- 상태: 승인됨
- 결정: `DEEPMINE_SCREENSHOT_SECTION` 실행 환경이 있을 때만 출정 안내, 준비 구역 4종, 실기기 관문 중 지정한 컨테이너 하나를 렌더링하고 XCUITest가 PNG로 첨부한다. 일반 실행에서는 전체 화면을 그대로 렌더링한다.
- 이유: 긴 단일 스크롤 화면에서 상태바 겹침, 오프스크린 잘림, 중복 구도 없이 각 기능 표면을 같은 시뮬레이터 조건으로 반복 캡처하기 위해서다.

## D-012 — P0 UI는 광산 출정 준비 흐름으로 표현한다

- 상태: 승인됨
- 결정: 기술 모듈명과 영문 상태를 주 정보에서 제거하고 `귀환 신호 → 갱도 문 → 시간·보급품 → 채굴 일지`의 실제 준비 순서로 재구성한다. 내부 API 이름은 진단 저장소에 유지하되 화면은 사용자가 누르는 이유와 예상 결과를 한국어로 설명한다.
- 이미지: 큰 장면은 ImageGen 원본을 384×216 또는 192×192 그리드로 축소하고 문서 고정 팔레트로 양자화한 뒤 최근접 확대한다. 24pt 광부는 D-016의 생성·후처리 스프라이트를 사용한다. 앱 아이콘은 40×40 판독 확인 후 1024×1024 불투명 마스터로 편입한다.
- 상호작용: 버튼은 4pt 하단 깊이와 press-down 이동으로 즉시 반응하고 Reduce Motion에서는 애니메이션을 제거한다. 본문과 조작은 전체 Dynamic Type을 따르며 그림 위 브랜드 표식만 XXXL로 제한한다.
- 이유: P0 기능을 숨기지 않으면서도 플레이어가 무엇을 준비하는지 이해하게 하고, 반복 카드·영문 계측·지표 격자가 주는 SaaS/개발자 도구 인상을 없애기 위해서다.

## D-013 — 광산 UI는 네 가지 안료와 장비형 조작으로 제한한다

- 상태: 승인됨
- 결정: 앱, Widget, Live Activity, 생성 에셋의 기본색을 석탄 `#10100F`, 혈암 `#373630`, 석회 `#E7E0CF`, 황동 램프 `#C58C39` 네 가지로 제한한다. 명도 단계는 이 안료의 불투명도만 사용한다.
- 상태 표현: 성공·진행·주의·실패는 별도 네온색을 추가하지 않고 `checkmark.seal/hourglass/exclamationmark.triangle/xmark.octagon` 문양, 문구, 채움/외곽선 차이로 구분한다.
- 조작: 주 동작만 황동으로 채우고 나머지는 혈암·석탄 금속판으로 낮춘다. 버튼과 패널에는 작은 리벳, 6–9pt 모서리, 4pt 하단 깊이를 사용하며 채굴 일지의 이진 상태는 사각 레일과 금속 손잡이를 가진 `Toggle`로 표시한다.
- 참고 경계: Behance 사례는 마모된 재료 체계, 제한 팔레트, 픽셀 실루엣에 대한 느슨한 영감으로만 사용하고 화면 구성과 에셋을 복제하지 않는다. 저장소와 상위 작업공간에서 `클로드디자인.md`는 발견되지 않았다.
- 테스트: 현재 시각 판정은 사용자의 요청대로 기본 `medium` 글자 크기·표준 대비·다크 모드에서 수행한다. 지원 기종 시뮬레이터에서 Dynamic Island compact/expanded 렌더링을 검사하되 AlarmKit 충돌과 승인 entitlement는 실기기 게이트로 유지한다.

## D-014 — DESIGN.md를 시각 언어의 기준 문서로 둔다

- 상태: 승인됨
- 결정: 루트 `DESIGN.md`를 색, 타이포그래피, 깊이, 버튼·패널·토글, Live Activity 표면의 기준으로 삼고 `.impeccable/design.json`을 도구가 읽는 동반 파일로 유지한다.
- 적용: 새 UI는 석탄·혈암·석회·황동 네 안료, 하나의 황동 주 동작, 리벳 금속판, 5–9pt 모서리, 플레이어 중심 한국어를 따른다. 새 색이나 별도 컴포넌트 문법은 먼저 이 문서의 결정을 갱신해야 한다.
- 이유: 이전의 SaaS형 카드·네온 상태색으로 회귀하지 않고 앱, Widget, 잠금화면, Dynamic Island가 같은 광산 장비처럼 보이게 하기 위해서다.

## D-015 — 리텐션 설계는 공정성을 먼저 검증한다

- 상태: D-018로 확정됨
- 결정: 퀘스트·시즌·소셜·수집 시스템을 구현하지 않는다. `docs/GAME_DESIGN_REVIEW.md`의 귀환 보고서, 세션 길이 성장 공정성, 심층 실패/일일 스트릭 계약을 먼저 확정한다.
- 잠금화면: Widget Extension과 캡처 하네스가 같은 최대 160pt 컴포넌트를 공유한다. 시뮬레이터 메뉴에서 실제 잠금이 불가능한 상태이므로 SpringBoard 합성·크롭·수명주기는 물리 기기에서만 통과 판정한다.
- 이유: 리텐션 기능의 수보다 완료 보상의 신뢰와 시간 투자 대비 공정성이 장기 복귀에 더 직접적이며, 빌드/시뮬레이터 증거를 실기기 검증으로 오인하지 않기 위해서다.

## D-016 — 24pt 광부는 생성 원본을 실제 픽셀 스프라이트로 후처리한다

- 상태: 승인됨
- 결정: 사용자 지시에 따라 단순한 코드 `Canvas` 도형을 제거하고 ImageGen으로 만든 광부 원본을 사용한다. 원본은 chroma key 제거 후 24×24 논리 그리드로 최근접 축소하고 석탄·혈암·석회·황동 네 색과 이진 alpha만 남긴다.
- 산출물: `MinerSprite.imageset`에 24×24, 48×48, 72×72 PNG를 넣고 앱과 Widget Extension이 같은 Asset Catalog를 사용한다. SwiftUI는 `.interpolation(.none)`으로 렌더링한다.
- 검증: 기본 `medium` 사양의 Dynamic Island compact/expanded, 160pt 잠금화면, 앱 헤더에서 헬멧 램프·얼굴·곡괭이·부츠가 구분되는지 캡처로 확인한다.
- 이유: 작은 표면의 셀 규격은 엄격히 유지하면서도 기존 직사각형 조합보다 캐릭터성과 채굴 맥락이 강한 실루엣을 제공하기 위해서다.

## D-017 — P0는 구현 차단이 아니라 릴리스 차단으로 전환한다

- 상태: 승인됨
- 결정: 2026-07-29 사용자의 명시적 전체 구현 지시에 따라 Spec §16의 P1–P4 게임을 시뮬레이터 우선으로 구현한다. 기존 P0 코드는 진단 경로로 유지한다.
- 검증 경계: Core 테스트, 시뮬레이터 앱 흐름, generic 빌드는 검증 가능하다. FamilyControls 승인, 실제 shield, AlarmKit/Live Activity 경합, App Group extension 경계, SpringBoard 잠금화면, StandBy와 Control Widget은 물리 기기 통과 전까지 `미검증`이다.
- 이유: 제품 전체를 구현하라는 현재 권한을 따르면서도 빌드 성공을 실제 시스템 동작으로 오인하지 않기 위해서다.

## D-018 — 집중 크레딧과 공정한 리텐션 계약을 채택한다

- 상태: 승인됨. 심도 기준은 D-024로, 프레스티지 보상은 D-025로 대체됨
- 진행: `focusedMinutes / 25`를 집중 크레딧으로 사용한다. 기본 보상은 `100 × credits`, 성장 `1.04^min(lifetimeCredits, 20)`, 심도는 run credits 기준이다. 15/25/50분의 보정은 ×1.0/1.1/1.3을 유지한다.
- 심층 실패: 해당 세션 보상만 잃고 이미 달성한 일일 목표와 스트릭을 소급 취소하지 않는다.
- 광맥: 기본 12%, 4회 이후 +8%p, 8회째 보장과 확정된 종류·효과를 `docs/BALANCE_REPORT.md`에 공개한다.
- 프레스티지: 첫 목표 40 run credits, 이후 ×1.6. 광석·장비·run depth를 초기화하고 수정·테마·기록·스트릭·영구 강화를 보존한다.
- 통계: 주간 집중 시간, 완료, 최고 심도, 계획 비율, 광맥 이력은 무료다. StoreKit과 상세 유료 분석은 현재 구현에서 제외한다.
- 이유: 짧은 세션 반복이 실제 집중보다 유리해지는 문제, 위험 계획이 이미 획득한 스트릭을 파괴하는 문제, 불투명한 무획득 구간을 동시에 해결한다.

## D-019 — 성장 지수는 20 집중 크레딧에서 상한을 둔다

- 상태: 승인됨. 광석 격차 가드레일만 D-026으로 대체됨
- 증거: 시드 260729 30일 시뮬레이션에서 무제한 `1.04^lifetimeCredits`는 헤비/라이트 누적 광석 격차가 261,767.864794배로 폭발했다. 프레스티지 때 지수를 초기화하는 안도 147.788782배였고, 프레스티지가 생산력 하락처럼 느껴지는 문제가 있었다.
- 결정: lifetime 기반은 유지하되 성장 지수 입력을 20 credits로 제한한다. 최대 성장 배율은 약 ×2.1911이며 프레스티지가 이를 낮추지 않는다. 페르소나의 일일 목표는 라이트/스탠다드/헤비/불규칙에 25/100/100/50분을 적용한다.
- 가드레일: 30일 집중 크레딧과 최종 심도 격차는 10배 이하, 모든 실제 보너스와 이탈률을 포함한 누적 광석 격차는 25배 이하로 회귀 테스트한다. 현재 결과는 각각 10.0배, 3.831386배, 24.585819배다.
- 이유: Spec이 의도한 20회 부근 ×2.2 체감을 보존하면서 장기 지수 폭발과 프레스티지 역보상을 함께 피한다.

## D-020 — 제품 SwiftData는 앱만 쓰고 시스템 표면은 snapshot과 명령을 사용한다

- 상태: 승인됨
- 결정: `GameRepository`가 제품 `DeepMine.store`의 유일한 writer다. 앱은 상태 변화 뒤 `GameSurfaceSnapshot`을 App Group에 원자적으로 게시하고 Widget/Control/Live Activity는 이를 읽는다. extension intent는 `GameCommand`만 enqueue한다.
- 명령: 장비·영구 강화·프레스티지는 SwiftData command ID와 상태를 같은 save에 기록한다. 시작·포기는 `GameStore`의 세션 상태 계약으로 처리한다. `open`은 상태 변이가 아니므로 앱 열기 경로에만 사용한다.
- 이유: Widget과 앱이 같은 SwiftData 그래프를 동시에 쓰는 구조를 피하면서 실제 시스템 표면이 최신 플레이 상태를 공유하고, crash window에서도 중복 진행을 막기 위해서다.

## D-021 — 귀환 보고서 소비 뒤 대기 상태를 명시적으로 게시한다

- 상태: 승인됨
- 결정: 귀환 보고서가 존재하는 동안 완료/광맥 snapshot을 유지한다. 사용자가 `마치기` 또는 장비 handoff로 보고서를 소비하면 저장 보고서를 지운 뒤 waiting snapshot을 게시하고 Widget/Control timeline을 새로고침한다.
- 이유: 보상을 보기 전에 수동 표면이 다음 세션으로 넘어가거나, 반대로 이미 소비한 보상이 위젯에 계속 남는 두 오류를 모두 막는다.

## D-022 — 리텐션은 강제 재생보다 공정한 다음 약속으로 제한한다

- 상태: 승인됨
- 결정: 홈의 한 가지 다음 약속, 오늘 목표/휴광일, 보장 광맥, 누적 장비·지역·테마, 무료 주간 회고, 귀환 3박자를 현재 MVP의 리텐션 체계로 삼는다. `마치기`와 `다음 출정 준비`는 동등한 위계다.
- 제외: 자동 재시작, 강제 스트릭, 소급 보상 박탈, 퀘스트/시즌/순위표, 푸시 압박은 구현하지 않는다.
- 이유: 사용자가 무엇을 했고 무엇이 다음에 열리는지 신뢰할 수 있어야 복귀가 지속되며, 실제 집중보다 게임 반복을 최적화하게 만들지 않기 위해서다.

## D-023 — 장비 효과를 복리로 전환하고 상한을 심도로 해금한다

- 상태: 승인됨 (2026-07-30, 사용자 지시)
- 증거: 선형 `+10%p`/비용 `1.38^n`에서 드릴 19레벨의 상대 이득이 +3.6%, 회수 1,094세션으로
  붕괴했다. 90일 시뮬레이션에서 라이트 페르소나는 60→90일 사이에 드릴 1레벨만 올렸다.
- 결정: 드릴 `1.12^(lv-1)`, 광차 25분 `1.05^(lv-1)`·50분 `1.07^(lv-1)`, 비용 `1.34^(lv-1)`,
  램프 +1.2%p/레벨에 기본가 200. 레벨 상한은 20에서 60으로 올리고 Spec §4.5대로
  `5 + 심도/60`으로 해금한다.
- 사양 관계: §16의 "20레벨"과 §4.5의 "심도가 장비 레벨 상한을 해금"이 충돌했고, 사용자가
  상한 인상과 밸런스 재조정을 함께 지시해 §4.5를 우선했다. §16의 숫자는 이 결정으로 대체된다.
- 결과: 어떤 레벨에서도 상대 이득 +12%가 유지되고, 180일에 네 페르소나 모두 사다리가 남는다.
- 이유: 클리커에서 지수 비용이 정당한 근거는 수입도 함께 지수 성장하는 것이다. 성장 지수에
  상한을 둔 D-019 이후 그 전제가 사라져 경제가 구조적으로 정체했다.

## D-024 — 심도는 lifetime 기준이며 프레스티지가 되돌리지 않는다

- 상태: 승인됨 (2026-07-30, 사용자 지시)
- 증거: run 기준 심도에서 30일 시뮬레이션의 스탠다드(하루 100분, 2회 프레스티지)가 291m·장비
  10·4·1로, 라이트(하루 25분, 0회)의 599m·11·8·6보다 낮았다. 4배 더 집중한 사용자의 정체성
  숫자가 더 작았다.
- 결정: `depth = floor(12 × lifetimeFocusCredits^1.15) + bonusDepthMeters`. `bonusDepthMeters`도
  프레스티지에 유지한다. 프레스티지 자격 판정은 계속 run credits를 쓴다.
- 대안 검토: (a) 회차 심도와 최고 심도를 함께 표시 — 한 숫자 원칙과 충돌. (b) 지역 임계값을
  회차마다 상향 — 이미 열린 콘텐츠를 다시 잠그는 벌칙. 둘 다 채택하지 않았다.
- 이유: 심도는 광산의 정체성 숫자이고 Spec §4.5는 원래 누적 기준이었다. 더 집중한 사람이 더
  얕게 보이는 것은 밸런스 오차가 아니라 리텐션 파괴다.

## D-025 — 프레스티지는 굴착 기억으로 재등반을 할인한다

- 상태: 승인됨 (2026-07-30, 사용자 선택)
- 증거: 1회차 조각 1개(영구 +8%)로 최대 ×21의 복리 장비를 초기화하는 교환은 장기적으로도
  회수가 어려웠다.
- 결정: 이전 최고 장비 레벨을 `rememberedEquipment`로 보존하고, 그 이하 레벨의 재구매 비용을
  50%로 한다. 조각은 `max(1, floor(runCredits/10))`, 굴착 기억은 `1.08^level` 복리.
- 이유: "굴착 기억"이라는 기존 이름과 컨셉에 그대로 맞고, 새 재화 없이 프레스티지를 순이익으로
  만든다. 회차마다 재등반이 2배 빨라진다.

## D-026 — 광석 격차 가드레일을 80배로 올리고 플레이 양 지표는 유지한다

- 상태: 승인됨 (2026-07-30)
- 결정: 30일 헤비/라이트 누적 광석 상한을 25배에서 80배로 올린다(관측 60.29배). 집중 크레딧
  10배와 심도 16배 상한은 유지하고, 심도 역전 금지와 180일 사다리 잔존을 새 회귀로 추가한다.
- 이유: 복리 장비는 광석 격차를 의도적으로 넓힌다. 순위표도 공유 경제도 없으므로 격차 자체는
  무해하며, 가드레일은 평준화가 아니라 폭주 감지를 위한 것이다. D-019의 광석 격차 부분만
  대체하고 성장 지수 20 상한은 그대로 둔다.

## D-027 — 시스템 표면 intent는 명령을 적재한 뒤 즉시 적용한다

- 상태: 승인됨 (2026-07-30)
- 증거: `StartSessionIntent`/`AbandonSessionIntent`가 App Group 큐에만 기록하고 소비는
  `scenePhase == .active`에서만 일어나, Dynamic Island의 재시작 버튼이 차단·알람·Live Activity
  없이 아무 반응도 만들지 않았다. 포기 버튼은 차단을 유지한 채로 남겼다.
- 결정: `LiveActivityIntent`가 앱 프로세스에서 실행되는 성질을 이용해, 앱이 실행 시 등록한
  `GameSurfaceCommandRunner`를 통해 enqueue 직후 drain한다. 큐 적재는 crash 내구성을 위해
  유지하고, 러너가 없는 위젯 프로세스는 기존 큐 전용 동작으로 폴백한다.
- 이유: Spec §1.2의 "Dynamic Island는 확인창이자 재시작 버튼"과 §19.3의 표시 계층 반증 조건이
  현재 구현으로는 구조적으로 달성 불가능했다. 차단 중 탈출 경로가 동작하지 않는 것은
  사용자 피해다.

## D-028 — 도전과제 보상은 수정과 외형으로만 지급한다

- 상태: 승인됨 (2026-07-30, 사용자 지시로 도전과제 도입)
- 결정: 도전과제 보상은 수정, 장식, 테마, 배지로 한정한다. 광석, 배율, 장비 레벨, 조각,
  광맥 확률은 **어떤 경우에도 지급하지 않는다.**
- 이유: 보상에 생산력을 넣는 순간 집중하지 않고 성장하는 경로가 생기고 Spec §1.2의
  "집중만이 유일한 연료"가 깨진다. 이 결정은 나중에 "배율 조금이면 괜찮다"로 흐려지기
  가장 쉬운 지점이므로 명시적으로 못박는다.
- 부수 효과: 수정은 현재 광맥에서만 나와 공급이 불규칙하다. 도전과제가 꾸미기 경제의
  안정적 공급원이 된다.
- 금지 조건: 하루 N세션, 분 단위 재시작, 자정 전 목표 달성처럼 과사용·압박을 유도하는
  조건은 만들지 않는다. §19.2의 폐기 지표와 `docs/GAME_DESIGN_REVIEW.md`의 윤리
  가드레일을 따른다.

## D-029 — 도전과제와 도감은 퀘스트가 아니다

- 상태: 승인됨 (2026-07-30, 사용자 지시)
- 사양 관계: Spec §16은 "퀘스트"를 제외 목록에 둔다. 도전과제와 광맥 도감은 이 목록과
  인접하지만 다른 것으로 판정한다.
- 구분 기준: 퀘스트는 **지시하고 기한이 있는 것**이고, 도전과제는 **이미 한 일에 이름을
  붙이는 것**이다. 도전과제에는 기한, 갱신 주기, 미달성 벌칙, 수락 행위가 없다.
- 이 구분이 흐려지면(일일 갱신, 만료, 실패 시 손실 중 하나라도 추가되면) 그것은 퀘스트이며
  §16 위반이다.
- 이유: 리텐션을 위해 도전과제를 넣으면서도 제품이 하루 할 일을 지시하는 도구로 변하지
  않게 경계를 문서에 남긴다.

## D-030 — 감각 피드백은 이벤트별로 구분되고 세션 중에는 침묵한다

- 상태: 승인됨 (2026-07-30, 사용자 지시로 플레이 경험 개선)
- 증거: 전체 앱의 오디오 자산이 0개, 시스템 사운드 1종, 햅틱 2종이었고 귀환 보고서에서
  단 한 번만 재생됐다. 갱도 봉인, 장비 강화, 광맥 발견, 도전과제 달성에 아무 반응이 없었다.
- 결정: `GameFeedbackEvent` 9종을 정의하고 각각 고유한 `GameHapticPattern`을 갖는다.
  CoreHaptics로 무게(intensity)와 날카로움(sharpness)을 구분하며, 미지원 기기에서는 UIKit
  제너레이터로 폴백해 무음이 되지 않게 한다.
- 경계: **세션 중에는 어떤 피드백도 발생하지 않는다.** 모든 이벤트는 플레이어가 직접
  일으킨 상태 변화이며, 세션 중 침묵은 Spec §6.1과 §14의 약속이다.
- 미구현: 커스텀 오디오 자산. 현재는 시스템 사운드 ID를 성격에 맞게 배정한 상태이며,
  8-bit 계열 SFX 저작은 별도 작업으로 남는다. `GameFeedbackEvent.systemSoundID`가 교체
  지점이다.

## D-031 — 반복 애니메이션 금지는 Live Activity에만 적용된다

- 상태: 승인됨 (2026-07-30)
- 결정: Spec §10.2의 `repeatForever` 미지원은 ActivityKit의 기술적 제약이다. 앱 화면에는
  적용하지 않으며, 활성 채굴 화면의 광부 작업 루프처럼 "광산이 돌아가고 있다"를 전달하는
  모션은 허용한다.
- 경계: Reduce Motion에서는 정지하고, 세션 중 알림·보상 카운터·가짜 발견 연출은 계속
  금지한다. 움직이는 것은 광부의 자세뿐이고 정보는 변하지 않는다.
- 이유: 세션 중 사용자를 방해하지 않는다는 원칙은 정보와 알림에 대한 것이지, 화면을 정지
  이미지로 만들라는 뜻이 아니다.

## D-032 — 연습 채굴은 10초이고 광맥을 확정 발견한다

- 상태: 승인됨 (2026-07-30, 사용자 지시)
- 결정: `demoDurationSeconds`를 90에서 10으로 줄이고, 연습 귀환이 수정 광맥을 확정
  발견한다.
- 광맥 종류: 푸른 광맥이 아니라 수정이다. 연습 광석은 고정 100이므로 푸른 광맥의 ×1.5를
  표시하면 지키지 못하는 약속이 된다. 수정은 실제로 1개 지급된다.
- 이유: 90초는 제품을 아직 보지 못한 사람에게 요구하기에 긴 시간이고, 광맥을 확률에
  맡기면 대부분의 신규 플레이어가 코어 루프의 핵심 기대감을 첫 실행에서 보지 못한다.

## D-033 — 활성 카운트다운 Live Activity는 AlarmKit이 단독 소유한다

- 상태: 승인됨 (2026-07-31, 잠금화면·Dynamic Island 결함 수정)
- 증거: 앱은 AlarmKit timer와 별도 `DeepMineActivityAttributes` Activity를 동시에 시작했지만,
  Widget bundle에는 `AlarmAttributes<DeepMineAlarmMetadata>`용 `ActivityConfiguration`이
  없었다. 시스템 countdown이 Dynamic Island에 표시될 계약이 빠진 상태였다.
- 결정: 활성 채굴은 AlarmKit timer 하나가 Lock Screen과 Dynamic Island를 소유한다.
  `AlarmAttributes<DeepMineAlarmMetadata>` 구성을 Widget bundle에 등록하고 게임 snapshot을
  metadata로 전달한다. 별도 커스텀 Activity는 AlarmKit 예약 실패 시 countdown 폴백과,
  앱 귀환 후 완료 표면에만 사용한다.
- 레이아웃 경계: `ActivityFamily.medium`은 iPhone 잠금화면과 StandBy가 공유하므로 레이아웃
  선택에 쓰지 않는다. `isActivityFullscreen`일 때만 StandBy, 그 외에는 160pt 잠금화면이다.
- 이유: 두 Activity를 동시에 시작하면 시스템 표면이 경합하거나 중복될 수 있다. AlarmKit의
  종료 신뢰성과 게임 전용 시각 표현을 유지하려면 소유권과 폴백을 분리해야 한다.
- 검증 경계: Widget 컴파일, 상태 투영, 메타데이터 왕복과 시뮬레이터 레이아웃은 자동화한다.
  실제 AlarmKit 표시·Dynamic Island·SpringBoard 수명주기는 실기기 릴리스 게이트다.

## D-034 — 광석 보상은 귀환 순간에 물리적으로 적재한다

- 상태: 승인됨 (2026-07-31, 광석 직접 재미 개선)
- 결정: 귀환 보고서의 큰 광석 숫자 아래에 획득량을 3–9개 덩어리로 추상화한 광차 적재
  연출을 둔다. 완료 햅틱은 작은 낙하 세 번과 무거운 광차 충돌 한 번의 리듬으로 맞춘다.

## D-039 — 기존 장비 3종을 클리커 역할로 재조준한다

- 상태: 승인됨 (2026-07-31, 구현 완료)
- 배경: 피벗 후 드릴/수레/램프는 각각 보상 배율, 세션 길이 배율, 광맥 확률이었다.
  세 가지 모두 집중 세션을 전제한 의미이고, 클리커에는 대응하는 개념이 없다.
- 선택지:
  - (a) 장비를 버리고 클리커용 업그레이드를 새로 만든다
  - (b) 이름만 남기고 의미를 바꾼다
- 결정: (b). 세 도구에 클리커 역할을 부여한다.
  - **드릴 = 손**. 탭 데미지. `drillRewardGrowthRate` 1.12 복리를 그대로 쓴다
  - **수레 = 기계**. 초당 자동 데미지. 기본 레벨에서는 0이고, 첫 업그레이드가

  - **램프 = 운**. 크리티컬 확률과 배율
- 이유: 가격 곡선, 심도 잠금, 재구매 할인, 업그레이드 조언자, 기억된 최고 레벨이 전부

- 수레 자동화를 0에서 시작하는 이유: "이제 알아서 돌아간다"는 아이들 게임이 팔아야 하는
  단 하나의 순간이다. 처음부터 주면 그 순간이 없다.
- 미해결: 60레벨 상한에서 자동 데미지가 3지역 근처에서 막힌다. 상한을 200으로 올리는
  것은 `docs/arc/plans/2026-07-31-long-run-progression.md`의 과제이며, 탭 데미지 입력이
  실제로 연결된 뒤에 검증 가능하다.

## D-040 — 심도의 진실 공급원을 부순 암반으로 옮긴다

- 상태: 승인됨 (2026-07-31, 구현 완료)
- 배경: D-032에서 심도를 `lifetimeFocusCredits` 기반 lifetime 값으로 바꿨다. 그때는 집중이

  - `NextStepPlanner`의 "가장 깊은 곳" 테스트가 크레딧이 아니라 세그먼트로 표현돼야 한다

## D-041 — 집중 증폭기의 가치를 1.5배~20배 대역으로 고정한다

- 상태: 승인됨 (2026-07-31, 구현 완료)
- 배경: 피벗 문서 §7이 지목한 위험. "입력이 둘이면 증폭기는 필수가 되거나 무의미해진다."

## D-042 — 가드레일을 불변식·대역·핀 세 등급으로 나누고 핀은 버린다

- 상태: 승인됨 (2026-07-31, 사용자 지시)
- 배경: 가드레일 다수가 뽀모도로 경제를 전제로 작성됐다. 전제가 사라졌는데 단정만 남아

- 밸런스 조정 시점: **탭 입력이 시뮬레이터에 반영된 뒤.** 지금 조정하면 게임의 절반만 보고

## D-069 — 장기 성장 경제의 진실 타입은 `BigNumber`다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 지갑, 암반 내구·보상, 데미지, 장비·정련 비용과 구매 결과, 추천 비용은
  `BigNumber`를 보존한다. `Double` 포화값을 구매 가능 여부나 사용자 표기의 진실로 쓰지 않는다.
- 경계: 시간, 확률과 화면 좌표처럼 유한 범위가 계약인 값은 `Double`을 유지한다.
  `NextStepPlanner` 진행도와 소스 호환용 `UpgradeRecommendation.cost` 투영은 아직 극후반
  `BigNumber` 계약 밖이며, 주요 화면은 `bigCost`만 사용한다.

## D-070 — 장기 선택성은 누적 광석이 아니라 심도 차이로 판정한다

- 상태: 승인됨·구현됨 (2026-08-02)
- 결정: 집중 사용량 차이에 따른 장기 경제 선택성은 누적 광석 비가 아니라 최고 심도 비와
  심도 역전 금지로 판정한다. 광석은 심도의 지수 함수라 자릿수 비가 플레이 품질을 직접
  뜻하지 않는다.

## D-071 — 집중 세션과 홈 채굴은 한 시간 예산을 공유한다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 세션 복구가 끝나기 전, 시작 버튼이 비동기로 세션을 준비하는 동안, 활성 집중 세션
  중에는 홈 `ShaftView`의 가시 타이머와 오프라인 정산을 모두 멈춘다. 실행 순서는
  `recoverSession → settleOfflineProduction`이며, 복구 실패 시에는 채굴을 열지 않는
  fail-closed 정책을 쓴다.
- 이유: 숨은 홈 채굴과 집중 귀환 보상이 같은 벽시계 시간을 각각 소비하면 한 시간을 두 번
  지급한다. 두 경제가 아직 완전히 통합되지 않았더라도 시간 소유권은 하나여야 한다.

## D-072 — 장시간 정산은 큰 carry window와 유한 패스 수를 함께 쓴다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 첫 해석은 기존 512세그먼트 상한을 유지하고, 절단 뒤 carry pass는 패스당
  `512 × 12 = 6,144`세그먼트를 처리한다. 전체 패스 수는 12로 제한한다.
- 결과: 한 호출의 순회 예산은 최대 `512 + 11 × 6,144 = 68,096`세그먼트다. 150km와
  500km의 8시간 오프라인 정산은 잔여 데미지 없이 끝나며, 더 큰 병적 입력은 잔여를 버리지
  않고 명시적으로 반환한다.

## D-073 — 첫 자동화는 효율 구매보다 우선하는 저축 마일스톤이다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 자동 생산이 아직 없으면 홈 추천은 광차 Lv.2 비용 ◆180을 절대 저축 목표로 유지한다.
  더 싼 드릴이 지금 구매 가능해도 추천을 바꾸지 않고, 광차 버튼만 충분히 모일 때까지
  비활성화한다.
- 이유: 첫 광차는 일반 효율 구매가 아니라 방치 게임이 시작되는 기능 해금이다.

## D-074 — 생산률과 구매 영향은 Core가 계산한다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: `WorkFaceForecast`가 자동 광석/초와 층/초를 `BigNumber`로 계산하고,
  `PurchaseImpact`가 구매 전후 탭 또는 자동 출력과 상대 증가율을 만든다. SwiftUI는 이 결과를
  포맷하고 표시할 뿐 자체 경제식을 만들지 않는다.
- 정련: 드릴·광차의 정련 도약과 램프의 기대 치명타 출력 변화를 구분한다. 램프는 레벨·영구
  강화의 가산값까지 포함한 실제 전후 치명타 배율을 계산하므로, 직접 ×2.5나 고정 ×√2.5로
  오표기하지 않는다.

## D-075 — 5/20/100km는 심연 내부의 시각 지질 경계다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 경제 지역은 기존 진입/수정/폐허/심연 네 구간을 유지한다. 심연 안에서만 5km
  pressure, 20km fault, 100km core 텍스처로 바꾸며 새 지역 보상이나 해금을 만들지 않는다.
- 렌더링: 화면이 경계를 가로지를 때 정확한 깊이에서 지층을 나눠 양쪽 세대를 함께 보여 준다.

## D-076 — 장기 진행 에셋은 버전·provenance·엄격 검증을 함께 보존한다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 선택된 에셋은 `-v2.png`로 버전하고, 매니페스트의 SHA와 Asset Catalog 선택 파일을
  검증한다. PNG CRC/zlib, 크기, 네 안료, 이진 알파/불투명, 앱·웹 복사본 일치를 표준 라이브러리
  검사기로 CI에서 확인한다.
- provenance: 손상된 pressure와 cart 2종은 이번 ImageGen 원본을 보존한다. 나머지 5종은
  이전 PR 원본을 정규화한 것으로 기록하며 출처를 새 ImageGen으로 소급하지 않는다.

## D-077 — PR은 Pages 배포 권한을 갖지 않는다

- 상태: 승인됨·구현됨·원격 검증됨 (2026-08-03 deployment closeout)
- 결정: PR은 정적 번들·smoke·artifact 계약까지만 실행한다. artifact 업로드와 배포는 main
  push에만 열고, `pages: write`와 `id-token: write`는 deploy job에만 부여한다.
- 이유: 코드 검증과 외부 배포 권한을 분리하고, PR이 Pages 설정을 변경하거나 배포를 시도해
  실패하는 구조를 제거한다.
- 원격 증거: GitHub Pages를 Actions source로 활성화했다. PR #3 병합 뒤 validation run
  `30770681257`과 Pages run `30770681254` attempt 2가 성공했고,
  `https://eiranotes.github.io/Deepmine/` 및 배포 `coreBalance.js`의 HTTP 200과 모듈 스모크를
  확인했다.

## D-078 — 장기 성장 필드는 모든 SwiftData 쓰기 경로에서 같은 계약으로 저장한다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: `GameRepository.save`, 명령 큐의 원자적 장비 구매, 세션 종료 커밋은 하나의
  `replaceState` 매핑을 사용한다. 현재/기억 장비, 정련 단계와 달성 업적을 어느 경로에서도
  빠뜨리지 않는다.
- 호환: 기존 저장소의 새 필드가 비어 있으면 기억 장비는 현재 장비, 정련은 없음, 업적은
  없음으로 읽는다. 직접 재열기, 명령 적용, 세션 보고서 소비 뒤 전체 상태 동등성을 각각
  회귀 테스트로 고정한다.

## D-079 — 웹은 공식 패리티 하네스이지 iOS 큰 수 런타임의 대체물이 아니다

- 상태: 승인됨·구현됨 (2026-08-02 current audit)
- 결정: 웹은 Core의 상수·공식·첫 광차 저축·램프 정련 식을 JavaScript로 대조하고 조기·중기
  UX를 확인한다. `number`의 표현 범위를 앱 `BigNumber`와 같다고 주장하지 않는다.
- 검증 경계: exponent 383 이상의 구매·지갑·생산률 정확성은 Swift Core/App 테스트가
  소유한다. 웹 패리티 성공은 수식 드리프트가 없다는 뜻이며 극후반 수 범위 동등성 증거가 아니다.
